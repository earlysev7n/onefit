## Architecture

**OneFit** is a Flutter gym app using Firebase Auth + Cloud Firestore, Provider state management, and free external APIs for exercise and meal data.

### State management

Five `ChangeNotifier` providers registered in `main.dart`:
- `ThemeProvider` — dark/light mode toggle
- `PlanProvider` — in-memory workout and meal plan for the current session; exposes per-day edit methods (`replaceExercise`, `removeExercise`, `addExercise`, `updateExerciseParams`) that each persist to Firestore immediately; also holds `setMeal(mealType, meal, saveToFirestore: true)` → `_saveMealToFirestore` which writes each `MealIngredient` item as its own `FoodItem` (scaled to grams)
- `ProgressProvider` — aggregates all weekly stats (food logs, workout logs, weight logs) for the Progress screen; call `loadAll(userId, {UserProfile? profile})` to refresh (pass the `ProfileProvider` profile to skip a redundant read); exposes `plannedWorkoutDays` (from `UserProfile.workoutDaysPerWeek`) and `weeklyWorkoutCompletion` using the real planned-days denominator
- `ProfileProvider` (`lib/providers/profile_provider.dart`) — **single reactive source of truth for the current user's `UserProfile`**. `load(uid)` fetches once and caches (no-op if already loaded); `refresh(uid)` force-refetches; `save(p)` persists + notifies (used by onboarding and the edit screen); `updateWeight(kg)` and `applyCalorieAdjustment(biasKcal)` are `copyWith`+`save` helpers. Home, Nutrition, Plans (`_WorkoutTab`/`_MealTab`) and Profile read it instead of fetching the profile independently, so a profile edit, a weight log, or a weekly calorie adaptation updates every screen reactively. Home calls `load(uid)` in `initState`; consumers `watch` it.
- `ConnectivityProvider` (`lib/providers/connectivity_provider.dart`) — see **Offline mode** below.

### Offline mode

Graceful degradation (Android). **Firestore's on-device persistence is the backbone** — it is on by default on Android and made explicit in `main.dart` (`Settings(persistenceEnabled: true, cacheSizeBytes: CACHE_SIZE_UNLIMITED)`), so every Firestore-backed read/write (profile, food/workout/weight logs, plans, weekly summaries) works offline: reads serve from cache, writes queue and sync on reconnect. `main()` also wraps `dotenv.load` in try/catch so a missing `.env` can't block cold launch.

**Writes must NOT be awaited for UI purposes.** A Firestore write's Future (`.set()`/`.delete()`/`.add()`) does not resolve until the server acks — **offline it never completes until reconnect**, even though the write hits the local cache instantly and streams surface it (`snapshots()` includes pending writes). So every write method in `FirestoreService` fires the write via `_fireWrite` (issues the local write, returns immediately, logs async failures via `catchError`) and reads (`.get()`) stay awaited (cache offline). `logFoodItem`/`saveWorkoutLog` generate the doc id synchronously via `collection().doc()` and return it without awaiting. `ProfileProvider.save` updates `_profile` **before** the (non-blocking) write so weight/profile edits and the calorie adaptation take effect in memory offline. This is what makes delete/regenerate-exercise and food-add work instantly offline instead of hanging until reconnect (the old bug: the UI `await`ed the ack). The `lastAdaptationWeekId` guard is set in memory optimistically, so the once-per-week adaptation still can't double-apply. **When adding a new write path, use `_fireWrite` / this pattern — never `await` a write before updating UI.**

`ConnectivityProvider` is the single source of truth for `isOffline` = real connection loss (`connectivity_plus`) **OR** the dev `forceOfflineEnabled` switch. The dev switch additionally drives Firestore's own `disableNetwork()`/`enableNetwork()` so it is a *real* offline test, not just a UI gate (real connectivity changes are left to the SDK). On every **offline→online transition** (after `enableNetwork()` flushes the queue) it fires callbacks registered via `addReconnectListener` — `HomeScreen` registers one that calls `ProfileProvider.recomputeGoal(uid)`, so the **daily weekly-adaptive goal re-syncs from the now-flushed logs**. It **never re-runs the weekly `AdaptationEngine`**; that stays guarded by `UserProfile.lastAdaptationWeekId` (applies once per week even across offline/online and force-regenerations), so offline→online can never double-apply a calorie bias. The whole algorithm/adaptive layer (`greedy_algorithm`, `adaptation_engine`, `weekly_adaptive_goal`, `calorie_tolerance`, `genetic_algorithm`, `progression`) is pure Dart and network-independent — untouched by offline mode.

The auto **offline banner** (`_OfflineBanner` in `main.dart`) renders in the `MaterialApp.builder` Stack when `isOffline`. Network-only features are **disabled with a friendly message** (never a raw throw) via `lib/widgets/offline.dart` (`isOffline(context)`, `showOfflineSnack`, `OfflineNotice`): USDA food search (`food_log_screen._search` — cached queries still served; fresh queries show the notice; `_loadMore` no-ops), barcode scan (`_scanBarcode` — blocked before opening the camera), meal generation (`plans_screen._startGenerateFlow`/`_generateAll`), and OpenAI recipe steps (`recipe_screen._fetchRecipe` — a *saved* recipe still loads from cache; only a fresh fetch is blocked). Workout generation is local and stays live offline.

### Navigation

No named routes. All navigation is `Navigator.push(MaterialPageRoute(...))`. The `AuthGate` in `main.dart` listens to `FirebaseAuth.authStateChanges` and routes to `LoginScreen`, `ProfileInputScreen`, or `HomeScreen`. `HomeScreen` is a `BottomNavigationBar` with 4 tabs: Home, Plans, Nutrition, Progress.

### Data layer

`FirestoreService` is a plain class (not a singleton) — instantiate it anywhere with `FirestoreService()`. Firestore structure:

```
users/{uid}                         ← UserProfile doc
  food_logs/{logId}                 ← FoodItem per logged meal/food
  workout_logs/{logId}              ← WorkoutLog when user marks a day done
  weight_logs/{logId}               ← WeightLog (one per day, doc ID = date string)
  exercise_stats/{exerciseId}       ← ExerciseStat (per-exercise last/PR top set; doc ID = exerciseId)
  workout_plans/{weekId}            ← persisted WorkoutDay list for that ISO week
  weekly_summaries/{weekId}         ← WeeklySummary (weekly adaptive report snapshot; doc ID = weekId)
  saved_meals/{docId}               ← SavedMealDoc (full Meal + recipe name, auto-ID)
exercises/{exerciseId}              ← ExerciseDB API cache (30-day TTL)
```

`workout_plans/{weekId}` is written by `FirestoreService.saveWeeklyWorkoutPlan` and read by `loadWeeklyWorkoutPlan`. The weekId is produced by `FirestoreService.weekIdFor(date)` → `week_YYYY_N` (normalised to Monday of that week, stable for the whole Mon–Sun range). `deleteWeeklyWorkoutPlan` removes the doc; used by the force-regenerate flow.

`weekly_summaries/{weekId}` holds the **Weekly Adaptive Report** — a `WeeklySummary` (`lib/models/weekly_summary.dart`) snapshot of one weekly adaptation event, written by `plans_screen._generate()` inside the **same once-per-week guard** as the calorie-bias application (`hasHistory && !alreadyAdaptedThisWeek`), so there's exactly one snapshot per `weekId` and force-regeneration never stacks it. It records the *reviewed* (prior) week's performance (calorie/protein adherence, workouts done/planned, avg `WorkoutLog.rating`, `daysLogged`, and `daysInTolerance` — how many logged days landed inside the ±5% `CalorieTolerance` band, computed in `_generate()` from the new `dailyCalories` list returned by `FirestoreService.getWeeklyNutritionSummary`, since the weekly average alone hides distribution; defaults to 0 on pre-tolerance docs) and the adjustments applied to the *active* week (calorie bias + old/new calorie goal, **derived** old/new macro targets, difficultyBias, `volumeChanged`, and the "why" notes). Macros are calorie-derived, not independently tuned — so `adjustmentBadge` has no "Increased Protein" (protein only rises when calories do). Persisted via `FirestoreService.saveWeeklySummary`; read by `getWeeklySummary` (current week) and `getWeeklySummaries` (history, ordered by `generatedAt` desc, no composite index). Surfaced in `WeeklyReviewScreen` (`lib/screens/weekly_review_screen.dart`, Current Week + History tabs), reached from a Progress-screen `_WeeklyReportCard` and from the post-generation "Weekly plan updated" snackbar's **View Summary** action. History starts empty and fills going forward (no backfill — past weeks were never persisted).

`UserProfile` stores all body stats and preferences. It computes `calorieGoal`, `tdee`, and `macroGoals` (macro gram targets) derived from Mifflin-St Jeor BMR + Harris-Benedict activity multiplier.

**UserProfile scheduling & recovery fields** (added in Phase 1/2; all have safe defaults for backward-compatible Firestore reads):

| Field | Type | Default | Role |
|---|---|---|---|
| `activityLevel` | String | `'Moderately Active'` | Drives `activityMultiplier` → TDEE → calorie goal |
| `workoutDaysPerWeek` | int | `3` | How many training days to place in the 7-day schedule |
| `sessionMinutes` | int | `45` | **Session-duration fit (Objective 4).** Drives the per-day exercise **count** via `_fitExerciseCount` (largest count whose sets×work + rests fit `sessionMinutes·60 − 180 s` warm-up; capped 6, ≤5 at ≥5 days/wk). Per-set sets/reps/rest stay pinned to the goal's NSCA range — never stretched to pad time, never scheduled over target (long NSCA-bounded sessions undershoot, accepted) |
| `workoutSplit` | String | `'Full Body Training'` | Maps to a focus-cycle sequence in `_splitFocusSequence()` |
| `trainingFocus` | String | `''` | **Prescription bias** `'heavy'\|'balanced'\|'high'` (empty → goal default via `effectiveTrainingFocus`). Decides reps/rest of the SELECTED exercises (`_getReps`/`_getRestSeconds`), never which are selected. User-overridable; legacy empty reproduces old goal-only reps |
| `avgHoursSlept` | double | `7.0` | Powers `recoveryScore` (< 6h → 0.7, 6–7h → 0.85, ≥ 7h → 1.0) |
| `calorieAdjustment` | int | `0` | Accumulated weekly calorie-goal bias, added on top of the goal-derived base in `calorieGoal` then clamped to the 1200 floor; fed by `AdaptationEngine.calorieBiasKcal` once per new `weekId` and clamped to ±500 by `ProfileProvider.applyCalorieAdjustment` |

`activityMultiplier` is now a real Harris-Benedict 5-tier lookup from `activityLevel` (not an experience+location proxy). Gender is stored as `'Male'` or `'Female'` only — no "Other" option; both Mifflin-St Jeor paths are used.

`UserProfile.pinnedExercises` (`Map<String,List<String>>`, focus → exercise ids, default `{}`) holds anchor lifts the user wants guaranteed in a given day focus; the greedy generator force-includes them first (see below). `UserProfile` is immutable; use `copyWith(...)` for edits (preserves `uid` and `calorieAdjustment`). The `calorieGoal` getter computes a goal-derived base (`tdee − 500` / `+ 300` / `+ 200` / `tdee`), adds `calorieAdjustment`, then clamps to `[1200, 99999]`; `macroGoals` reads `calorieGoal`, so macros scale automatically.

**Weight is a single reactive value.** `UserProfile.weight` drives BMR/TDEE/`calorieGoal`/BMI; logging today's weight on the Progress screen calls `ProfileProvider.updateWeight(kg)` (persists + notifies → Home/Nutrition rings recompute) **and** `ProgressProvider.logWeight(uid, kg)` (saves the `weight_logs` entry + reloads Progress). The two stores no longer drift.

Weight and height are always stored in metric (kg/cm) internally; display conversion happens in `UserProfile.weightDisplay` / `heightDisplay`.

### Algorithms

- `GreedyAlgorithm` (`lib/algorithms/greedy_algorithm.dart`) — generates a 7-day `List<WorkoutDay>` from a `List<Exercise>` and `UserProfile`. `_getSchedule(profile, {weekIndex})` places training days and cycles through the split's focus sequence (`_splitFocusSequence`). **`workoutDaysPerWeek` is a hard constraint** — adaptation never adds or removes training days. **Schedule shapes by focus-sequence length / split:** (1) **Full Body / Functional / Strength+Conditioning** (1-focus, or the non-Upper/Lower 2-focus S+C) → evenly-spaced positions across the week; (2) **legacy 5-focus** (Bro/Body-Part) → packed consecutively; (3) **Upper/Lower** (2-focus, matched by `workoutSplit == 'Upper / Lower Split'`) → **PAIRED ("connected")**: Upper+Lower back-to-back then a rest after each pair (`Upper Lower R Upper Lower R R` for 4 days); an odd trailing day is always the **first focus (Upper)** — fixed, no rotation (`seq[i%2]`); no cap, so non-rest count == `days`; (4) **3-focus** (PPL, legacy Hybrid) → **a rest follows each completed triple**, and 3-focus splits are **capped at 6 effective training days** (`min(days,6)`) so a PPL week always keeps ≥1 rest (a 7-day selection trains 6, `PPL R PPL`). The **first triple always restarts Push/Pull/Legs** in order every week; only a **partial trailing block** (days 4–5) **rotates by `weekIndex`** (0-based weeks since `createdAt`, computed in `plans_screen._generate()`), so the "extra" day advances Push→Pull→Legs across weeks — a full second triple (day 6) uses natural order, no rotation. Rotation only takes effect on **fresh generation** (each new week / force-regenerate); the persisted-plan load path keeps the stored schedule. The PPL and Upper/Lower paired schedules share the placement helper `_placeWithCycleRests(sessions, cycleLen)` (rest after each completed cycle, capped by `7 − sessions.length`). **Session-duration fit (Objective 4):** the per-day exercise **count** comes from `_fitExerciseCount(profile, …, sets, restSeconds, work, poolSize)` — the largest count whose `count·sets·work + (count·sets−1)·rest` fits the `sessionMinutes·60 − 180 s`(warm-up) budget, capped at 6 (≤5 at ≥5 `workoutDaysPerWeek` — frequency temper); it never schedules **over** target, and NSCA-bounded volume that can't fill a long session undershoots (accepted, by design). `_estimateWorkSeconds(reps)` sizes the per-set work-timer (~3 s/rep + setup, timed moves use their value, clamp 30–75 s) — UI countdown only, not a loading parameter. **NSCA grounding:** `_getReps`/`_getSets`/`_getRestSeconds` are pinned to the NSCA goal-loading ranges (Sheppard & Triplett, *Essentials of S&C* 4th ed.) — hypertrophy 6–12 reps/3–6 sets/30–90 s, muscular endurance ≥12/2–3/≤45 s, general 8–15/2–4/30–90 s; `_getSets` clamps to the goal's set range, then shaves a set when `recoveryScore < 0.8` and applies ±1 for `difficultyBias` (re-clamped to range). **Training-Focus prescription (three-axis refactor):** `_getReps(profile, category, role)` is now driven by `UserProfile.effectiveTrainingFocus` (`'heavy'|'balanced'|'high'`, defaulting to the goal: Weight Loss/Endurance→high, Muscle Gain/General→balanced) × goal × per-exercise **role** — `_assignRoles` labels the day's first compound `mainCompound`, later compounds `secondaryCompound`, the rest `isolation` (assigned over the DISPLAY order, so the main lift leads). Heavy → lower reps everywhere (main 4–6 / sec 6–8 / iso 8–10); High → 10–12 compounds / 12–15 iso; Balanced → a goal-dependent MIX by role (`_balancedReps`, never a flat range — e.g. Muscle Gain main 4–8, iso 10–15). `_getRestSeconds(applyFocus)` nudges rest (heavy +30 s, high −15 s, clamped [30,180]). **Training Focus is prescription only — it never changes selection:** the exercise COUNT budget (`_fitExerciseCount`) uses focus-INDEPENDENT reps (`_countBudgetReps`) + rest (`applyFocus:false`), so changing focus changes reps/rest but never how many exercises are picked. `GreedyAlgorithm.represcribeDay(profile, orderedExercises)` re-derives reps/rest (preserving each exercise's set count) so a persisted plan tracks a Training-Focus change on load without a regenerate (wired in `plans_screen` after the display sort). `generatePlan` accepts optional `difficultyBias` (`'up'`/`'down'`/`'same'`) only — it has **no** `calorieBiasKcal` parameter. The weekly `AdaptationEngine.calorieBiasKcal` is applied to the calorie goal via `ProfileProvider.applyCalorieAdjustment(bias, markWeekId:)` in `_generate()`'s fresh-generation branch, not passed into the workout generator. The calorie nudge is guarded by an explicit `UserProfile.lastAdaptationWeekId` stamp (compared to the current `weekId`) so it applies **once per week even across force-regenerations** — force-regenerate deletes the plan doc and re-enters the fresh branch, which would otherwise re-add the bias and stack the drift. The adaptation snackbar is gated on the same `!alreadyAdaptedThisWeek` flag, so it shows once per week (silent on regens). `difficultyBias` is recomputed every regeneration but is idempotent on identical last-week data, so a regenerated plan keeps the same difficulty (it is deliberately not persisted). The `AdaptationEngine` also takes an optional `weightChangeKg` + `fitnessGoal`: a weight-trend modifier nudges calories ±100 for `'Weight Loss'`/`'Muscle Gain'` goals, but only when adherence didn't already move them (non-stacking). `_generate()` only runs the `AdaptationEngine` when last week has real history (a persisted plan or ≥1 workout log) — otherwise a new user's empty week reads as 0% completion and wrongly triggers `'down'`.

Home equipment chips: Bodyweight (locked), Dumbbells, Kettlebells, Resistance Bands, Pull-up Bar, **Barbell** (chip covers `barbell` + `ez barbell`), **Bench**, **Home Gym** (= power/squat rack; selecting it auto-adds Barbell + Bench in the UI and is the rack flag in eligibility). Gates: the **rack rule** (`_rackTag = \b(squat|bench press)\b`) blocks barbell squat/bench-press unless `Home Gym` is owned — floor-start barbell work like deadlift/row/OHP/hip-thrust passes on a bare Barbell chip; the **bench rule** (`_benchTag = \b(incline|decline|bench)\b`) blocks free-weight bench moves unless `Bench` is owned (bodyweight variants already passed). Barbell is **not** gym-only in `_inferLocations` (so it's home-eligible when owned). The strict experience gate is `static difficultyAllowed(difficulty, level)`. **Physical limitations** are the first check in `isEligibleForUser` (before the gender/gym/bodyweight branches, so they apply to Gym users and block even bodyweight moves like burpees): `exerciseBlockedByLimitations(e, p.physicalLimitations)` (`lib/data/physical_limitations.dart`) hard-excludes exercises via **one always-on layer** over the single source of truth `kPhysicalLimitations` (10 affected areas, each with an RRL citation). Selecting an area (its id in `UserProfile.physicalLimitations`) blocks its **full mapping**: the auto-block set (`categories`/`muscles`/`keywords`) **and** every mapped `AvoidableMovement.keywords` (movements used to be an opt-in checklist — now always applied when the area is selected). The 10 areas: Asthma, High Blood Pressure, Shoulder Pain, Knee Pain, Lower Back Pain, Wrist Pain, Elbow Pain, Hip Pain, Ankle Pain, Neck Pain. `limitationReasonFor(e, areaIds)` returns the offending area id (for the picker warning). Empty list = no-op (existing users unaffected); keywords are precise (e.g. `back squat`, not bare `squat`). This is a *broad* exclusion — movement-heavy areas (Knee/Lower-Back/Hip) can thin a training day — but the generator degrades gracefully (assist-mover + bodyweight fallback + undershoot) so a day is never empty (asserted across every limitation by the `test/greedy_scoring_test.dart` matrix). `UserProfile.avoidedMovements` is now **vestigial** (kept for old-doc back-compat; profile input writes `const []` and no logic reads it). **The exercise picker is the escape hatch, not a hard block:** in `plans_screen`, limited moves are *shown* and route through the existing `_restrictionsFor` → `_confirmRestrictions` **"Add Anyway"** dialog (equipment/tier warnings share this flow); an amber warning icon flags them in the list. **Automatic paths stay hard** — generation, gap-fill (`_fillExerciseGap`), volume-debt (`_applyVolumeDebt`) and swap go through `_usableByUser`/`isEligibleForUser`, so they never auto-inject a limited move. The profile input chips are a plain toggle (tap = select/deselect, no sheet). Not medical advice — the profiling UI carries a disclaimer. Asserted in `test/limitation_filter_test.dart`. **Intensity-caution modifier (Asthma / High Blood Pressure only):** these two areas set `PhysicalLimitation.intensityCaution = true`, so beyond the hard exclusion they *also* act as a conservative **prescription modifier** layered on top of the fitness goal — `limitationsReduceIntensity(areaIds)` (`physical_limitations.dart`) gates it. In `GreedyAlgorithm`: `_getSets` subtracts one set (floored at 2 working sets, re-clamped to the goal's set range) and `_getRestSeconds` adds +45 s rest (ceiling 210 s); both are **scoped to the real prescription only** — the session-fit COUNT budget calls `_getSets(applyLimitation:false)` / `_getRestSeconds(applyFocus:false)`, so exercise selection and per-day count are unchanged (same pattern as Training Focus). **Reps are never modified** — they stay goal-driven (`_getReps`/`_countBudgetReps` untouched). `ConditioningFinisher.apply` returns the plan unchanged (no high-intensity finisher) when `limitationsReduceIntensity` is true. This dosing is OUR conservative choice **informed by** (not a verbatim protocol from) ACSM Hypertension FITT recommendations, ACSM's exercise-for-hypertension guidance, and the rest-interval literature (PubMed 36196336) — cited in `physical_limitations.dart` — which support conservative progression, appropriate resistance volume, and longer recovery intervals. Public test wrappers: `setsForDifficulty` / `restSecondsForProfile`. Asserted in `test/limitation_modifier_test.dart`. **Age prescription modifier (older adults ≥ 65):** the **same** conservative dosing seam, gated by `ageReducesIntensity(age)` (`lib/data/age_prescription.dart`, threshold `kOlderAdultAge = 65`, ACSM/WHO older-adult line) instead of a limitation flag. `UserProfile.age` (already collected for BMR, no new UI) drives it: `_getSets` subtracts `_kAgeSetReduction` (1 set, same 2-set floor) and `_getRestSeconds` adds `_kAgeRestBonus` (**+30 s**, gentler than the medical +45), **stacking additively** with the limitation modifier and sharing the extended 210 s rest ceiling. Dosing is OUR conservative choice **informed by** (not a verbatim protocol from) ACSM's older-adult exercise guidance — cited in `age_prescription.dart`. Unlike the medical caution, the age modifier does **not** suppress the `ConditioningFinisher` (cardio is beneficial for older adults). The **bucketed** gate `ageReducesIntensity(age)` (not raw age) is in `UserProfile.workoutGenerationSignature`, so a persisted plan regenerates only when the user crosses 65 (the only point the dose changes) — needed because `represcribeDay` re-derives reps/rest on load but preserves set counts.   - **Selection is incremental greedy** (`_selectExercisesForDay`): pick best, update day-local muscle hits, re-score, repeat — plus a per-muscle-per-day cap (`ceil(count/targets)` clamped ≥2). **Day focus is a HARD pool constraint, not a score:** candidates are restricted to `primaryPool` (a primary muscle in `musclesForFocus(focus)`), falling back to `assistPool` (focus muscle as a *secondary* mover) only to reach `count`; if both are exhausted the day stays **shorter** rather than ever pulling in an off-focus muscle. (Focus was previously only a +50 score — but the accumulating weekly penalty −15/hit could exceed it on late-week days, letting a never-targeted muscle like forearms outscore a worked focus muscle → "wrist curl on Leg day". The hard filter fixes this.) Within the focus pool the score is **profile-driven** (`_scoreExercise`): `Score = focus +50 (structural anchor) + clamp(GoalScore + ExperienceScore, −20..+45) + muscle-balance (−25/day-hit, −15/week-hit, structural anchor)`. The middle block's weights are **selected from the user's `UserProfile`** (Fitness Goal / Exercise Priority, Experience Level) rather than fixed constants, so the same eligible pool ranks differently per user. **`sessionMinutes` is deliberately NOT a ranking term** — it only sizes the per-day exercise **count** via `_fitExerciseCount`, so a short session yields fewer exercises without overriding which *type* the user prioritised (a top-ranked isolation is never demoted just because 30 min was chosen). **GoalScore is exercise-TYPE only** (the three-axis refactor — selection, coverage, and prescription are kept separate). The middle block = `goalMatch (fixed +15 when exercise.goals∋ goalKey) + exerciseType`. `exerciseType` (`_exerciseTypePoints`) reads the user's **Compound-vs-Isolation** ranking: every exercise is compound (`isStapleCompound‖isHeavyCompound`) XOR isolation, so the preferred type scores **+2** and the other **+1** — a small tie-breaker (gap 1, deliberately far below the +50 focus / −25/−15 balance anchors so type taste only breaks genuine ties). **Foundational-lift bonus:** when Compound is the preferred type, a true heavy barbell/dumbbell compound (`isHeavyCompound` — bench/squat/OHP/row/deadlift) additionally gets `_kHeavyCompoundBonus` (**+6**) so the big lifts are selected ahead of lighter/bodyweight compound variants of the same muscle (still inside the [−20,+45] clamp; Isolation-preferring users unaffected; Training Focus stays prescription-only). **Classification:** `isStapleCompound` now checks an `_isolationKeywords` guard (raise/fly/curl/extension/kickback/pullover/pushdown/shrug/pec deck/rear delt/wrist) **before** the `secondaryMuscles.length >= 2` heuristic, so isolations that list ≥2 secondaries (e.g. front raise) are no longer miscounted as compound. **Exactly one** type value is ever awarded, so a Compound+HeavyLift move (Bench Press) no longer stacks two features and a Isolation+HighRep move (Cable Fly) no longer stacks two — this is the double-count the refactor removes. **Heavy Lift, High Rep and Full Body are NOT selection scores:** Heavy/High are the *prescription* (Training Focus, see the reps bullet above) and Full Body is *workout-structure coverage*, enforced structurally by the day-focus pool + per-muscle cap (a move is never picked *because* it hits ≥4 muscles). The Compound/Isolation order is stored as the 2-item Compound/Isolation list in `UserProfile.goalPriorities` (the profile screen edits a tappable Compound/Isolation choice + a 3-way Training Focus selector, and `_reconstructGoalPriorities` stores that order on save; legacy 5-item lists still read fine — everything past compound/isolation is ignored); `_scoreExercise` reads only the compound-vs-isolation order, falling back to `GreedyAlgorithm.defaultGoalPriorities(fitnessGoal)` (a fixed **compound-first** default for every goal; the app has **no "Strength" goal**) for empty/legacy lists. The old `_goalWeights` table + `goalFeatureKeys` were **removed** as vestigial (only compound-vs-isolation is ever consumed); `goalFeatureLabels` keeps just the Compound/Isolation UI labels. `goalMatch` stays a **fixed +15** (not user-rankable). This is **orthogonal to the weekly adaptive system** — `goalPriorities` lives on the profile (survives every `copyWith`, incl. `applyCalorieAdjustment`), and adaptation's `difficultyBias` only nudges set counts, never feature scoring. **ExperienceScore** is graduated via `static const _experienceWeights[level][difficulty]` (Beginner→beginner +8; Advanced→advanced +10/intermediate +6/beginner +2), gated by `difficultyAllowed`. **There is no TimeScore** — `sessionMinutes` affects only the exercise **count** (`_fitExerciseCount`), never ranking (the old `_timeScore` term was removed so time can't override the user's Exercise Priority). The **+45 clamp** keeps the personalised block from overpowering the balance penalties — a repeated-muscle pick still loses to a fresh-focus pick, keeping the "wrist-curl-on-leg-day" regression fixed. Location/equipment/limitations/gender carry **no** score weight (they're hard filters upstream → constant across survivors). The public `scoreExercise` wrapper (used by PlansScreen's picker sort + gap-fill) delegates here, so manual-edit ranking stays consistent with generation. Compound-first holds on day 1; later days may lead with an isolation on a fresh focus muscle (by design — variety/balance). **On-card display order groups muscles big→small** via `GreedyAlgorithm._muscleSizeOrder` (legs → chest → back → shoulders → arms → core; `cardiovascular system` leads on cardio days): `musclesForFocus` sorts each focus's muscles by it, so every multi-muscle day (Full Body, Upper/Lower, PPL) shows the big movers first — the `_focusMuscleMap` lists are membership-only. Asserted in `test/greedy_scoring_test.dart` (a sampling-matrix golden test proving safety/structure invariants across every input axis + that the ranking responds to goal/experience/time).

- `CalorieTolerance` (`lib/algorithms/calorie_tolerance.dart`) — pure Dart. **The single source of truth for "on target"**: a ±5% band around the calorie target (`fraction = 0.05`, `lowerPct` 95 / `upperPct` 105; 3000 kcal → 2850–3150, both edges inclusive). Rationale: dietary assessment carries measurement error, so reported/estimated intake differs from actual intake (National Academies of Sciences, Engineering, and Medicine, 2023) — a difference inside the band is noise, not a deviation worth acting on. Three consumers read it and can therefore never disagree: (1) `ProfileProvider._computeDailyGoal` via `effectiveWeekConsumed` — see the daily-goal bullet; (2) the `AdaptationEngine` calorie branch; (3) `weekly_review_screen._adherenceTag(pct, useTolerance: true)` for calories (protein keeps its looser 90/110 band, matching its own 85% engine threshold) plus the `Days on Target` row. **There is deliberately no daily on-target label** — a `CalorieStatusChip` was built and then removed: the Home card already shows `Goal` beside `Eaten`, and the Nutrition ring already shows "N kcal left" above `Goal / Eaten / Remaining` cards, so any On/Under/Over pill was restating a number the screen showed twice already. The band's daily job is the redistribution and the `+N` badge, not a label. **Notification trigger:** `shouldAnnounceGoalShift({daysOutOfTolerance, adjusted, base})` = `daysOutOfTolerance > 0 && adjusted != base` — the trigger is a **day that breached the band**, never the size of the resulting nudge, which is small by construction once diluted across the remaining days (a 212 kcal breach with 6 days left is only +35/day; gating on that kept the dialog silent for exactly the weeks that mattered). Asserted in `test/calorie_tolerance_test.dart`.

- `AdaptationEngine` (`lib/algorithms/adaptation_engine.dart`) — pure Dart, no Flutter/Firebase. Takes last week's calorie adherence, workout completion rate, and the week's per-session ratings → returns `AdaptationResult` with `calorieBiasKcal` and `difficultyBias`. **Calories:** adherence outside the shared `CalorieTolerance` band moves the goal ±100 kcal — `< 95%` → `+100`, `> 105%` → `−100` (was a hand-tuned 85/110); inside 95–105% is a dead zone. The `> 105%` cut is still skipped for a Weight-Loss user who is actually losing (outcome beats intake), and the weight-trend modifier still only fires when adherence produced no bias. The protein note now requires calories to be *within tolerance* (`CalorieTolerance.withinPct`) while protein is `< 85%` — protein keeps the looser bar because protein logging is noisier. Difficulty: completion `< 0.5` → `'down'` **first** (struggling user eased off); otherwise completion `≥ 0.8` (non-Advanced) → `'up'`; else `'same'`. The week's `lastWeekRatings` (a `List<int>` of per-session `WorkoutLog.rating`, 1 too easy … 5 too hard) then refine it via a **vote** (1→+2, 2→+1, 3→0, 4→−1, 5→−2): sum `≤ −2` eases `'down'` (overrides an up/same baseline), sum `≥ +2` steps `'up'` — but a **safety brake** (any single `5` "too hard", or completion `< 0.5`) forbids stepping up, and the easy-bump still requires completion `≥ 0.7` (don't reward a partial-skipper). Sleep is no longer an input (removed). `_generate()` passes last week's ratings list in (and keeps the mean only for the `WeeklySummary` display). Vote combos asserted in `test/adaptation_engine_test.dart`.
- `GeneticAlgorithm` (`lib/algorithms/genetic_algorithm.dart`) — **the meal generator** (per the capstone objective). The Meal tab is split into two modules: **Module 1 — Meal Planning** (Generate Meal, before eating) and **Module 2 — Nutrition Tracking** (Log Food, what was actually consumed — unchanged food logging; logging updates daily totals reactively and never triggers generation). Ingredients are loaded via `FirestoreService.getIngredients()` (in-memory cached; `FirestoreService.clearIngredientCache()` drops it after a re-seed) and seeded with `SeedData.seedIngredients()` (Profile screen button, gated by `kShowSeedTools`).
  - **Generate Meal flow (Module 1).** A meal card's **Generate** button (`plans_screen._startGenerateFlow`) opens an option sheet: **Option A — Use Available Ingredients** pushes `FoodLogScreen(pickerMode: true)` (multi-select USDA search / barcode / history, *no grams asked*), converts picks to per-100g `MealIngredient`s via `IngredientConverter` (`lib/services/ingredient_converter.dart`, pure Dart), and runs `optimizeMealPortions` — chromosome = **gram vector** over the fixed picked set (every usable pick appears exactly once; tournament selection, single-point crossover, single-gene jitter mutation, top-2 elitism; fitness = `_mealFitness` vs the meal's calorie budget + `_mealShareTargets`). **Option B — Generate Automatically** runs the existing `evolveMeal` over the seeded pool. Either result is reviewed on the **accept-mode `RecipeScreen`** (fresh OpenAI recipe from names+grams only, full ingredients + expandable macro/micro nutrition summary, Accept / Regenerate buttons; OpenAI failure still allows "Accept Without Recipe"). **Accept** persists through the standard `PlanProvider.setMeal(saveToFirestore: true)` `ai_generated` path — accepted food IS logged food (tap a logged row on the card to edit grams/servings or delete via `_showEditLoggedFood`, which writes only the `quantity` multiplier). Regenerate re-runs the same option (Option A keeps the picked pool and ignores `avoidIds` — a fresh RNG explores new gram vectors; Option B passes the shown ingredient ids as `avoidIds`). Asserted in `test/meal_portion_optimizer_test.dart` + `test/ingredient_converter_test.dart`.
  - **Option A dietary-restriction layering.** Picked USDA/barcode foods carry no `dietaryTags`, so inclusion tags are NOT required by `optimizeMealPortions` — instead: (1) the picker blocks restricted foods outright (search already `DietaryFilter`-filtered; history filtered in picker mode; a conflicting barcode scan is rejected with a message; `_addPicked` re-checks), (2) `_startGenerateFlow` pre-screens the pool with `DietaryFilter.violates` before the GA, (3) `optimizeMealPortions` drops allergen-conflicting (`dairy`/`nuts`) and zero-kcal ingredients. Empty pool after any layer → empty-meal sentinel → "No ingredients match your dietary restrictions" (restrictions are never relaxed). `DietaryFilter.matchesDairy`/`matchesNuts` are public so `IngredientConverter.deriveAllergens` shares the guards (nut butters carry both flags — the filter's long-standing conservative `'butter'` false positive).
  - **Dietary restrictions are split into three kinds** (`_passesRestrictions` + `_macroTargetsFor`). The profile offers exactly: restrictions {Vegetarian, Vegan, Halal, Lactose-intolerant, Nut-free} (multi-select) + a single-select diet style {High-protein, Low-carb, Balanced}. (1) **Inclusion tags** — Vegetarian/Vegan/Halal (and legacy Gluten-free) require the matching `MealIngredient.dietaryTag`. (2) **Exclusion allergens** — Lactose-intolerant → reject `allergens` containing `dairy`; Nut-free → `nuts`. (3) **Macro styles** — High-protein (40/35/25 P/C/F) and Low-carb (35/20/45) override the `fitnessGoal`-derived macro targets used by `_fitness`; Balanced keeps `UserProfile.macroGoals`. **`MealIngredient` now carries `allergens` and `category`** (protein/dairy/grain/legume/vegetable/fruit/fat/condiment/other), derived at seed time by `SeedData._deriveAllergensAndCategory(name)` and stored in Firestore so the runtime GA reads concrete fields, never ingredient names.
  - **Pool selection is fail-SAFE** — dietary restrictions are *never* dropped. If the cuisine narrows the pool to empty, the cuisine alone is relaxed; if even the restriction-only pool is empty, `generatePlan` returns an **empty list** (sentinel) and the Meal tab shows "No ingredients match your dietary restrictions" rather than serving violating food. The snack pool is drawn from the same filtered `pool` (so it honours cuisine + restrictions + the condiment blacklist). The fail-safe ladder is `buildPool(allIngredients, profile, cuisine)` (public; also drops any `calories <= 0` ingredient — a seed-time USDA miss — so a 0-kcal record never reaches a meal), shared by `generatePlan` and `completeMeal`. Asserted in `test/meal_restriction_matrix_test.dart` (`flutter test`). The Meal tab's "Add ingredient" affordance on a generated meal opens the full USDA search (`FoodLogScreen`), same as "Log Food" — it does not use this pool.

Generate All retains the **pending/"Log Additions" staging** (green rows on the card; `_logPendingMeal` persists only the new `ai_generated` items — no double-save), while single-meal Generate goes through the accept-mode review instead. `evolveMeal` complements what's logged via `presentCategories` (computed from logged `FoodItem`s by `_inferCategory`, which delegates to `IngredientConverter.inferCategory`). `completeMeal` (the older single-draw completion) is **no longer wired to any UI** — kept for `test/meal_completion_test.dart` and as the documented slot-plan reference; `generatePlan`'s 7-day path is likewise test-only. Budget/complement behavior asserted in `test/meal_completion_test.dart`.
  - **Calorie accuracy — `scaleToCalories` + `closeResidual`.** `completeMeal` (and `_normalizePlan`) chain `Meal.scaleToCalories(target).closeResidual(target)` (`lib/models/meal_ingredient.dart`). `scaleToCalories` proportionally scales portions but clamps each item to 30–**400**g (was 350 — the mismatch with `_portionFor`'s 400 caused systematic under-delivery on low-density meals). `closeResidual(target, {tolerance:30, maxPasses:3})` then closes the gap the clamp truncated: it distributes `target − totalCalories` across items **densest-first** (densest needs fewest grams), re-clamping each to 30–400g and accounting for what the clamp absorbs, over ≤3 passes; stops when within 30 kcal or every item is pinned at a clamp edge (physical limit — only happens with pathologically low-density pools). This generalises the old dinner-only fine-tune to all meals/all items. Asserted in `test/meal_accuracy_test.dart` (meals land within ±75 kcal across density ranges).
  - **Weekly adaptive daily goal (rule-based, provider-level, for today only).** `WeeklyAdaptiveGoal.adjust({base, weekConsumed, daysLeft, clamp:0.10})` (`lib/algorithms/weekly_adaptive_goal.dart`, pure) spreads the week's *remaining* budget across the remaining days so the user still hits their weekly target after over/under-eating earlier in the week: `target = (base·7 − weekConsumed) / daysLeft`, clamped to `[base·(1−0.10), base·(1+0.10)]`; returns `base` when `daysLeft ≤ 0`. Applied independently to calories, protein, carbs and fat. `ProfileProvider` (`lib/providers/profile_provider.dart`) computes this at `load()`/`refresh()` time via `_computeDailyGoal(uid)` (sums this week's logs Mon→yesterday) and exposes `dailyEffectiveGoal` (int) + `effectiveMacroGoals` (Map). **Only meaningful calorie deviations are redistributed:** `_computeDailyGoal` buckets the week's logs per day and passes `CalorieTolerance.effectiveWeekConsumed(dayTotals, base)` as `weekConsumed` — a day inside the ±5% band is booked as exactly `base`, so ordinary logging noise never moves tomorrow's goal. **Days with no logs are excluded entirely** — `daysElapsed` is now the count of *logged* days, not calendar days since the anchor, because a day with no data is missing data rather than a zero-calorie day (counting it as a full shortfall used to inflate today's goal by up to +10% and pop the "Today's Goal Adjusted" dialog at anyone who forgot to log). `WeeklyAdaptiveGoal.adjust` itself is untouched (the normalisation lives in the caller); **macros stay on raw sums** — the tolerance rationale is about energy intake. The provider also exposes `daysInToleranceThisWeek` / `daysLoggedThisWeek` / `daysOutOfToleranceThisWeek` (the notification trigger) and `lastBreachKcal` (signed deviation of the most recent out-of-band day, quoted in the dialog copy; per-day buckets are keyed by normalised `DateTime` and sorted so "most recent" doesn't depend on query order). (Supersedes the old `DailyCarry` yesterday-only carry-forward, now fully deleted.) **All display screens** (Home, Nutrition, Plans Meal tab, Progress, Profile) read `profileProvider.dailyEffectiveGoal` instead of `profile.calorieGoal` — so the adjusted number is the visible, app-wide goal for today. `ProgressProvider` receives it via `loadAll(effectiveGoal:)` for the today-ring and chart; however, `ProgressProvider.calorieAdherence` (the weekly %) still uses `profile.calorieGoal` as the denominator so it stays consistent with the weekly `AdaptationEngine`. **This is deliberately isolated from the weekly system:** it never writes `calorieAdjustment`, is never persisted (provider-level transient state), and `UserProfile.calorieGoal` / `AdaptationEngine.compute()` / `WeeklySummary` are all untouched. Asserted in `test/weekly_adaptive_goal_test.dart`.

- `FoodItem` — a single logged food entry; holds full macro + 14 vitamin/mineral fields; `barcode: 'ai_generated'` means it came from meal generation
- `EdamamRecipe` — the recipe model returned by `EdamamService`; `PlanProvider.logEdamamRecipe()` remains in place (unused by current meal-tab flow, available for future recipe features)
- `WorkoutLog` / `WorkoutLogExercise` — saved when user taps "Mark as Done" on the Plans screen; streamed to Home screen workout card via `FirestoreService.streamWorkoutLogForDate()`. `WorkoutLog.rating` (1–5, optional) is the post-workout perceived-difficulty rating (feeds `AdaptationEngine`). **Per-set logging:** `WorkoutLogExercise.loggedSets` (`List<SetEntry {weightKg?, reps?, seconds?}>`) is what the user *performed*, one entry per set logged live in the session (weight+reps for loaded lifts, reps-only for bodyweight, seconds for timed) — distinct from the *prescribed* `sets`/`reps`. `skipped` flags an exercise the user skipped (not counted as completed volume, never progressed). ### Meal saving — one path in PlanProvider

**GA-generated meals** (`setMeal → _saveMealToFirestore`): Each `MealIngredient` inside a `Meal` is saved as its own `FoodItem` (scaled to the actual portion grams, `barcode: 'ai_generated'`). This is the sole meal-generation save path — the GA produces the ingredient list; logging it writes each ingredient individually. `logEdamamRecipe` remains in the codebase for future use (e.g. a recipe feature) but is not called by the current meal-tab generate flow.

### PlansScreen — exercise cache pattern

`PlansScreen` keeps a `List<Exercise> _allExercises` state variable used by the exercise picker and gap-fill logic. **This must be populated on every code path:**
- `_generate()` always fetches exercises via `ExerciseDBService().getExercises()` **before** checking for a persisted plan, so both the load-from-Firestore and generate-fresh branches have `_allExercises` set.
- `initState` kicks off a background `getExercises().then(...)` for the hot-restart path (in-memory plan already present, `_generate()` not called).

Failing to follow this pattern results in "No matching exercises found" in the picker.

### PlansScreen — plan persistence & force-regenerate

Plans are persisted per ISO week to `users/{uid}/workout_plans/{weekId}`. The refresh `↺` button calls `_forceRegenerate()`, which deletes the Firestore doc via `PlanProvider.clearAndDeleteWorkoutPlan()`, then calls `_generate()`. This is the escape route from a corrupted plan.

`PlanProvider.persistWorkoutPlan` refuses to write if every training day has 0 exercises. `loadWorkoutPlan` refuses to accept such a plan from Firestore. Both guards prevent the "broken plan locked forever" failure mode.

When a persisted plan is loaded, `_generate()` runs `_sanitizePlanForProfile(plan, profile)` after rehydration: it drops exercises that fail the **current** profile's `isEligibleForUser` + `difficultyAllowed`, then refills each day back to its original size from the eligible pool (bodyweight is always eligible, so days never empty). It re-persists only if something changed. This is what prevents a plan generated under Gym (or older equipment/level) from keeping gym/barbell/machine moves after the user switches to Home — without it the rehydrate step preserves stale exercises verbatim.

Edit mode enforces a 50% minimum exercise cap (cannot remove more than half the original count). Removing exercises without replacing them triggers an AlertDialog offering either auto-fill (`_fillExerciseGap`) or a volume-debt penalty (`_applyVolumeDebt`) that adds 1 extra exercise to the next 1–3 upcoming workout days.

### PlansScreen tab navigation

`PlansScreen` has two tabs — Workout (index 0) and Meal (index 1). To switch programmatically:
- Pass route arguments `{'mealType': '<type>'}` when pushing `PlansScreen` — `didChangeDependencies` picks this up and animates to the meal tab.
- Call `plansScreenKey.currentState?.switchToMealTab()` directly — `plansScreenKey` is a `GlobalKey<PlansScreenState>` defined in `home_screen.dart`.
- Call `plansScreenKey.currentState?.startWorkout()` (the Home "Add → Start Workout" quick action) — animates to the Workout tab, then forwards to the workout sub-tab's state via a private `GlobalKey<_WorkoutTabState>` (`_startWorkout` lives on `_WorkoutTabState`, not `PlansScreenState`). Because `body: screens[_currentIndex]` mounts `PlansScreen` fresh on switch, `startWorkoutFromHome` polls (`_awaitPlanThenStart`, ~50 ms × 40) until the plan finishes loading before calling `_startWorkout`; it no-ops if the day is already in `_weekDone` (completed) or a session is running.

### UI design tokens

All screens share a consistent dark theme. Use these constants inline (they are not extracted to a theme file):

| Token | Value | Usage |
|---|---|---|
| Background | `Color(0xFF0D0D0D)` | Scaffold background |
| Surface/card | `Color(0xFF1A1A1A)` | Cards, bottom sheets, tab bars |
| Primary accent | `Color(0xFF00C97B)` | Buttons, progress indicators, active tab |
| Muted text | `Color(0xFF888888)` | Secondary labels |
| Header font | `GoogleFonts.spaceGrotesk` | Titles, headings (`w700`) |
| Body font | `GoogleFonts.inter` | Body copy, labels |

**Text scale.** Every `fontSize:` in `lib/` is an *authored* value that gets multiplied at
render time — `AppTextScale.resolve()` (`lib/theme/app_text_scale.dart`) is wired into
`MaterialApp.builder` in `main.dart` and is the only place the app's type size is set.
`AppTextScale.bump` (1.08) lifts the authored sizes, which ran 1–2pt under the platform
norm, putting the dominant 13px body on the 14px Material baseline; `AppTextScale.maxTotal`
(1.30) caps the *total* (OS accessibility scaling × bump) so the bump can never stack on an
accessibility setting. So `fontSize: 13` renders at ~14 — **write authored values, not
rendered ones**, and keep **11 as the floor** (nothing in `lib/` declares a size below it).
1.08 is the largest bump at which every label still fits: at 1.15 the Home calorie card runs
out of room and `Remaining` clips to `Remaini…`, so going bigger means widening that card's
label column first. Asserted in `test/app_text_scale_test.dart`.

**When touching a fixed height that holds text, do not "unbind" it.** Swapping
`SizedBox(height: n)` for `ConstrainedBox(minHeight: n)` is *not* a safe refactor: the
`SizedBox` passes a **tight** constraint, and subtrees here rely on it — `Column`s default
to `MainAxisSize.max` and `Center`/`Align` without a `heightFactor` both expand to fill
whatever they are given. Loosening the constraint makes them grow to the parent's maximum.
That is exactly how the bottom nav bar in `home_screen.dart` was once made to swallow the
whole screen. If such a box genuinely needs to grow, scale the tight value
(`SizedBox(height: MediaQuery.textScalerOf(context).scale(n))`) rather than removing the
upper bound.

### Debug flags

`_DEBUG_FORCE_LOGOUT` in `main.dart` — set to `true` to force sign-out on every hot restart during auth testing. Must be `false` before any build intended for real use.

**Developer Mode** (`developerModeEnabled` in `lib/app_clock.dart`) — a runtime `ValueNotifier<bool>` (persisted to `SharedPreferences` key `developerMode`, restored in `main()`), toggled by the **Developer** section at the bottom of the Settings screen. It replaces the old compile-time `kDebugDayChanger` const. When on, the Settings section reveals the demo toolset; turning it **off** resets `devDayChangerEnabled = false`, `debugDayOffset = 0` and `forceOfflineEnabled = false` so a real user is never left on a shifted day or forced offline. The tools:
- **Force Offline** (`forceOfflineEnabled`, `ValueNotifier<bool>` in `lib/app_clock.dart`) — simulates no connection for testing offline mode without touching Wi-Fi. `ConnectivityProvider` treats it as offline (banner + disabled network features) and also calls Firestore `disableNetwork()`/`enableNetwork()` so it's a real cached-reads/queued-writes test. See **Offline mode**.
- **Change Day** (`devDayChangerEnabled`, `ValueNotifier<bool>`) — shows the floating ◀ date ▶ pill (wired via `MaterialApp.builder` in `main.dart`) that shifts the app's notion of "today" for date-dependent flows (weekId, today's plan/meals, streaks, weekly adaptation, where new logs land). All *logical* date reads go through `appNow()` / `appToday()` (which now read `devDayChangerEnabled.value ? debugDayOffset.value : 0`) instead of `DateTime.now()`; real-time concerns (cache TTLs, unique IDs, workout-duration timers, `Timestamp` parse fallbacks) intentionally still call `DateTime.now()`. Changing the day re-pushes a fresh `HomeScreen` (via the `debugDayOffset`/`devDayChangerEnabled` listeners on `_onDayChanged`), so everything re-reads for the simulated day.
- **Demo Scenario** (`devScenario`, `ValueNotifier<DevScenario>` — `levelUp`/`easeOff`/`realistic`) — picks what last week's seeded data makes the `AdaptationEngine` do.
- **`DevTools`** (`lib/dev/dev_tools.dart`, pure helpers over `FirestoreService`) — `autoCompleteToday(context)` logs today's planned workout as done; `simulateWeekAndAdvance(context, scenario)` seeds the current week with workout + food logs for all 7 days (shaped by the scenario — see the scenario table), persists the week's plan so it counts as "last week" history, then bumps `debugDayOffset += 7`. Opening the Plans tab afterwards makes `PlansScreen._generate()` fire the once-per-week adaptation (calorie bias + difficulty) and save a `WeeklySummary`. Scenario knobs: `levelUp` → calories ~80% of goal + all workouts done + rating 1 (→ +100 kcal & difficulty up); `easeOff` → ~40% completion + rating 5 (→ difficulty down); `realistic` → calories ~83% + ~67% completion + rating 3 (→ +100 kcal, difficulty held).

All Developer Mode state must be **off** for any build intended for real use (it defaults off and is never enabled without the Settings toggle).

### Misc

- `lib/data/seed_data.dart` — one-off dev utility that seeds exercises and ingredients from USDA FDC into Firestore. Not called at runtime; ignore unless seeding.
- `lib/services/openai_service.dart` — `OpenAIService.generateRecipe({ingredients, mealType})` calls the OpenAI Chat Completions API (`gpt-4o-mini`, JSON response) to turn a GA meal's ingredient list (with gram portions) into step-by-step cooking instructions → `OpenAIRecipe(title, steps, readyInMinutes, servings)`. Wired into `RecipeScreen`, which has two modes: **view mode** (Recipe button on a meal card; loads/saves the cached `users/{uid}/saved_recipes/{mealType}` doc) and **accept mode** (`acceptMode: true`, the Module-1 review step; always fetches fresh, pops `'accept'`/`'regenerate'`/null back to `_reviewAndAccept`). OpenAI receives only ingredient names + GA-fixed grams and never changes quantities — the GA is the source of truth for nutrition. API key is a hardcoded constant (move to env config for production).
